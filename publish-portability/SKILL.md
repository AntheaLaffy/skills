# 发布可移植性：装得上 ≠ 装完能用

发布物里任何「作者机器的事实」——家目录、用户名、绝对路径、钉死的环境变量、本机才有的
二进制——都会让别人的机器「能装、功能全断」。这类 bug 在作者机器上永远测不出来：
作者环境恰好就是写死的那一个。发布前用「别人机器」的视角过一遍，且验的是**发布物**
而不是仓库；仓库干净 ≠ 包干净。

## 检查清单

1. **grep 作者痕迹**（仓库 + 拆包产物）：

   ```sh
   rg -n "/home/|C:\\Users|<你的用户名>|<你的机器名>" --glob '!node_modules' --glob '!.git'
   npm pack --pack-destination /tmp && tar -xzOf /tmp/<pkg>.tgz package/*.js | grep -n "/home/"
   ```

   例外要能说出「为什么」：注释引用本地路径、测试夹具不算发布物，但打包名单里的文件都算。
2. **默认值运行时推导**：`homedir()`、`os.tmpdir()`、XDG 目录、相对路径、`import.meta.url`。
   安装脚本创建的东西，按「安装它的那个用户」解析，不按开发者解析。
3. **子进程环境**：默认继承宿主环境；要覆盖某个变量，先回答「这个值在别人的机器上是什么」，
   答不上来就是硬编码。宿主运行时已做环境清洗时不要覆盖它做对的默认值
   （如 DSH 的 subprocess 保留 HOME/PATH、剥掉凭据形变量）。
4. **配置/装载补丁不写死**：preset、patch、installer 里的 `config` 缺省即走运行时推导的
   默认值；补丁里写绝对路径等于替每个用户选了错误答案。
5. **前置依赖摆在明面**：二进制/服务/守护进程不在包里时，README 与商店描述必须写明装什么、
   怎么启动、监听哪里；描述里的数字、命令、端口都会被评审拿代码核对。
6. **副作用披露 + 可关**：往用户目录写文件、软链、改全局配置，必须披露并给关闭开关；
   不声不响改用户机器是打回理由。
7. **回归测试防复发**：断言「不出现 `/home/`」「默认值落在 homedir 下」「spawn 不钉 HOME」，
   live 冒烟不传机器专属配置。
8. **验发布物而非仓库**：打包产物、registry 下载的包、release 资产各 grep 一遍。
9. **别人机器心智演练**：干净 `$HOME`、另一账号、空容器走一遍 安装 → 启动 → 核心功能。
   作者机器上这套流程永远全绿——这正是它测不出 bug 的原因。

## 被打回时

- **先修代码再补描述**：描述解决不了「装完功能全断」；前置说明写得再好，工具还是断的。
- 评审给了描述文案就直接采用，回评带证据（commit、测试、拆包结果），只说「已修」等于没回。
- 修完发 PATCH；索引/商店等 registry 可见新版本再同步，不要提交旧索引。
